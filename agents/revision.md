# Targeted revision

The revision command propagates a single human-directed change — a corrected fact, a reshaped concept, a renamed element — through the project's active working set. It is the lateral complement to the pipeline: pipeline steps move a draft forward through passes; a revision fixes one thing everywhere it currently lives, so the working set stays consistent with itself.

The revision command is not a pipeline step. It has no `step_id`, appears in no recipe, and **never touches `pipeline-state.md`** — no checkbox, no `last_updated`. It is a host command (the `/revise` slash command in Claude Code; the `revise` agent in OpenCode) whose thin adapters point here; this file is the canonical contract.

## Invocation

`revise <change description>` — the change description is prose: what is wrong and what should be true instead. The human may request a new draft version by saying so anywhere in the request ("as a new draft", "make a new version", or equivalent); absent that request, the draft is revised in place. Parse the request tolerantly — the human is describing a change, not writing a strict CLI. If no change description was given, ask the human what to revise and stop.

**Confirm-only invocation.** A request may instead name an entry and state that it is correct as written, with no proposed change — e.g. "confirm the harbor-lights entry in the voyage log" or "that timeline fact is right, mark it reviewed." This is a second, equally legal invocation shape, parsed the same tolerant, prose-not-CLI way as a change description. It applies to any of the five destinations already in this command's edit scope below — `canon/generated/*`, `characters/<id>/timeline.md`, `characters/<id>/profile.md`, `continuity/`, and `knowledge/` (character files are already "always edited in place" per `## Edit scope`). If the request is ambiguous about whether it is a confirmation or a correction, ask (Procedure step 1).

## Edit scope

**Always edited in place, in both modes:** character files (`characters/`), canon files (`canon/`), the chapter's active storyboards (`<chapter-folder>/storyboards/`), and the **current-state entries** of the objective-continuity files (`continuity/`). These files carry current truth; they are not versioned, and the corrected fact has no other home.

**The draft, by mode:**

- **In-place (default):** edit `<latest-draft>` — the attempt manifest's active head — in place. No new file is minted, no manifest entry is added, and the `Active-head:` pointer does not move.
- **New-draft (on request):** leave the active head's file untouched; write the revised prose as `<next-draft>` and record it in the manifest per the draft-write rule in the Procedure below.

**Surfaced, not edited by default:** occurrences of the old shape anywhere else in the active working set — plan files (`<story-plan>`, scene lists, summaries), `open-questions.md`, notes and reports, aftermath files. Name them in the closing report; edit them only when the request covers them or the human widens scope when asked.

**Never edited:** `pipeline-state.md`; side-artifact `Reviewed-draft:` stamps; manifest entries for existing drafts; the **transition structure** in the non-destructive temporal-state files' `## Superseded` / `## Lost or superseded` sections (`continuity/`, character `knowledge/`) — the `id`, the held-from/to range, and the `superseded-by` link that record *when* a fact changed diegetically, which a revision never fabricates, re-times, or deletes (a superseded entry's stored *value* may itself need an authorial correction — see below); and archived material — any attempt directory other than `<latest-attempt>`, any `draft-vNN.md` other than the draft being revised, and any directory the consuming project keeps as an archive (e.g. a root `archive/`). Superseded and archived files record what was true when they were written. A revision changes the present, never the record.

**Current state vs. the record (non-destructive temporal-state files).** The temporal-state files that record change non-destructively — `continuity/` (objective facts) and M14's character `knowledge/`, `timeline.md`, and `relationships.md` — hold two kinds of thing a revision treats differently. A **current-state entry carries current truth**, so an authorial revision corrects it **in place**, keeping its `id`. A **`## Superseded` / `## Lost or superseded` transition records that a fact changed *diegetically*** — its `id`, its held-from/to range, and its `superseded-by` link — and a revision **never fabricates, re-times, or deletes that structure**, nor adds a transition of its own: the story-internal change a transition records really happened, and inventing one would fabricate an in-story change that never did. This is the diegetic-vs-authorial distinction stated once in `agents/continuity.md`.

A superseded entry still stores a **value** — the objective fact as it stood at that earlier position — and that value can itself be authorially wrong. When the human revision changes *what was always true* about a fact whose current home is a superseded entry — correcting who held a post *before* a later, genuine hand-over that has already moved the fact to `## Superseded` — correct that entry's **value in place, keeping its `id` and its transition structure**. Leaving it forbidden would strand the authorially-rejected value as the maintained answer for that earlier position, and the revision would never reach the active continuity state. This is still an in-place authorial correction (no new transition); it simply lands on a superseded entry, because that is where the fact now lives.

**Provenance follows the corrected prose (new-draft mode).** An in-place correction to a continuity entry — current or superseded — rewrites its stored value, but the entry is still `committed-in`/`evidence`-stamped against a draft. In **new-draft mode**, where the corrected prose lands in `<next-draft>` and the old active draft is left unchanged, also move the entry's `committed-in` and full `evidence:` pointer to `<next-draft>`, so the fact cites the prose that actually supports it; leaving them on the old draft — which still carries the rejected value — makes the entry immediately `derived-unsupported`.

**The same restamping is required, and more load-bearing, when the entry actually carries a `committed-in:` field — which is not every entry.** `knowledge/` entries always do: `scene_knowledge_update` (`agents/steps/scene-knowledge-update.md`) stamps every entry it writes with the full attempt-qualified path `<chapter-folder>/drafts/<attemptNN>/draft-vNN.md`, never a bare `draft-vNN.md` basename (a bare basename repeats across chapters and attempts and would false-fresh on a collision; `agents/characters.md`). `timeline.md` entries are **not uniform**: the fuller, `templates/timeline.md`-documented shape carries the same `committed-in:` field and the same restamping rule below applies to it — but a **capture-agent-written** `timeline.md` entry (the Rule 1 `invented, unreviewed` inventions this confirmation lifecycle is actually about) carries no `committed-in:` at all, only the inline scene/beat/attempt annotation (`agents/capture/capture-agent.md`'s Write discipline: "an inline note or trailing tag riding alongside the new entry" — no structured field minted). Neither carries a separate `evidence:` field to move.

Where a `committed-in:` field is present, its freshness predicate (`agents/characters.md`, "Freshness is derived, never stored") is **lineage-only**: an entry is fresh iff its stamped attempt equals the source chapter's latest attempt **and** its stamped draft is in the active head's lineage — there is no `derived-unsupported` content-resolution axis the way `continuity/` has. Restamping is therefore not optional hygiene here as it is for continuity's self-flagging case: it is required **whenever the entry's existing `committed-in:` does not already name the draft the correction actually lands in**, regardless of mode.

- **New-draft mode** always requires it: the corrected value lands in `<next-draft>`, a file the old stamp cannot already name. As part of the same Apply edit (step 6) that corrects the value, restamp `committed-in:` to the full attempt-qualified path `<chapter-folder>/drafts/<latest-attempt>/<next-draft>` — not the bare `<next-draft>` basename, which is exactly the ambiguity this field's contract exists to rule out. `<next-draft>`'s own manifest entry names the old draft as its `read_from:`, so the old draft stays in the active head's lineage; a corrected entry left stamped against it would read as **fresh**, not flagged, even though that old draft still carries the rejected value the correction just replaced — silently letting downstream relational checks (`compliance_report`) treat unsupported character state as settled.
- **In-place mode** usually needs no restamp, because the entry's stamp typically already names the file being edited — the active head, `<latest-draft>` — the same shape that lets a continuity correction skip the move below. But an entry can be stamped against an **older draft that is still in the active head's lineage** (fresh under the lineage-only predicate without being the most recent draft); an in-place revision always writes `<latest-draft>`, not that older file, so a correction there still lands in `<latest-draft>`'s text while the stamp keeps naming the older one. Restamp `committed-in:` to `<latest-draft>`'s full attempt-qualified path in that case too — the same failure (a correction whose stamp still names a draft that never received it) is otherwise reachable in either mode.

**A capture-agent-written `timeline.md`/`profile.md` entry has no `committed-in:` to restamp, in either mode, and this paragraph does not apply to it.** Its inline scene/beat/attempt annotation records where the fact was originally invented, the same fixed-provenance shape `canon/generated/`'s entries carry (Apply, step 6, above) — not a live freshness pointer, since neither destination has a draft-lineage freshness predicate to begin with. A correction to such an entry's value leaves that annotation as-is; only the `unreviewed`→`confirmed` marker flip (or the corrected value, on a correct-and-confirm request) changes.

For a **continuity** entry whose stamp already names the file being edited, in-place mode needs no move: the corrected prose keeps the same filename the stamp already names (`agents/orchestrator.md`, Artifact-state — the freshness predicate compares filenames, not content).

## Procedure

1. **Restate the change.** Before editing anything, state it as old truth → new truth in a sentence or two, and proceed on that statement. On a **confirm-only** request, restate instead what is being confirmed, and proceed once the human confirms it. If the request is ambiguous — two readings, an unclear boundary, or unclear whether it's a confirmation or a correction — ask the human now. The revision command runs with the human present: ask directly, in-session; do not write questions to `open-questions.md` that the human can answer immediately. A confirm-only request skips only step 3 below (there is no source content to fix) — it still runs step 4 (Sweep, read-only, if useful context) and step 6 (Apply, whose only edit, for confirm-only, is the marker flip itself; skipping it would perform no write at all and could report success while leaving the entry unreviewed). Close with step 8's report as usual.
2. **Resolve paths.** Read `amanuensis-project.yaml` for `project_type`; resolve `<chapter-folder>`, `<latest-attempt>`, `<latest-draft>`, and (in new-draft mode) `<next-draft>` per `agents/project-layouts.md`.
3. **Fix the source of truth first.** Find the file where the changed fact canonically lives — a character profile, a `canon/` file — and correct it before touching anything downstream, so every later edit has a settled target to align to.
4. **Sweep.** Search the whole project for the old shape: keyword matches first, then the mentions a keyword search cannot find — scenes that paraphrase, remember, report, or apply the changed element without using its words (a memory of the advice, a later retelling, a consequence of the fact). Classify every hit: in scope (edit), outside the default scope (surface), archived or superseded (leave). When the changed fact is a maintained objective fact, its `continuity/` entry's `evidence:` pointers name the accepted-prose locations that committed it — use them to index the prose ranges the sweep must re-check.
5. **Check the guardrails.** `agents/update-rules.md` applies in full. Two points bear restating here. An element marked immutable may still be revised — immutability markers exist to stop agent-initiated drift, and a human-directed revision is exactly the authority that may move one — but name the marker and confirm the new shape with the human before editing it. And reveal timing (Rule 2) binds a revision like any other edit: the new shape must not let a character or the reader know something earlier than the story allows.
6. **Apply.** Edit each file in its own register: storyboard and canon edits stay in storyboard and canon language; prose edits are made in the character's voice and the surrounding rhythm, never by mechanical find-and-replace. Verify every downstream echo against the new shape, including the ones that turn out to need no edit. **When the edited entry itself already carries an `unreviewed` confirmation marker** — in any of the five destinations, `canon/generated/*`, `characters/<id>/timeline.md`, `characters/<id>/profile.md`, `continuity/`, `knowledge/` — flip that marker to `confirmed` (the vocabulary defined in `agents/update-rules.md`'s Confirmation subsection) as part of this same edit; for a confirm-only request, this marker flip is the entry's only edit. Flip the per-entry inline tag for `canon/generated/*`, `timeline.md`, and `profile.md` (e.g. `invented, unreviewed` → `invented, confirmed`); flip the `- **review:** unreviewed` field to `- **review:** confirmed` for `continuity/` and `knowledge/`. For `canon/generated/*` specifically, flip only the confirmed entry's own inline tag — never the file-level frontmatter `status:`, which this confirmation lifecycle never reads or writes, for any entry. This is a **destination-plus-marker** gate, not a destination-only one: `continuity/`/`knowledge/`/`canon/generated/` entries always carry the marker (every entry these writers produce is stamped, per `agents/steps/continuity-update.md` / `agents/steps/scene-knowledge-update.md` / `agents/capture/capture-agent.md`), but `timeline.md`/`profile.md` routinely mix capture-agent inventions with ordinary human- or step-authored entries that carry no marker at all — e.g. the narrative sections `templates/profile.md` defines. Editing one of those carries no flip: there is no `unreviewed` state to close, and fabricating an `invented, confirmed` tag on an entry that was never `invented, unreviewed` would misrepresent its provenance.
7. **Write the draft (new-draft mode only).** Write the revised prose to `<next-draft>`; append a manifest entry with `produced_by: revision`, `read_from:` naming the draft revised (the active head), a `timestamp` (ISO 8601 with timezone offset), and `review_gate: false`; repoint `Active-head:` to the new draft. Reading the active head makes this a linear advance — supersede nothing (the lineage and supersession algorithm in `agents/project-layouts.md` governs).
8. **Verify and report.** Re-run the sweep and confirm the old shape survives only where it is meant to (archives, superseded attempts, surfaced-but-unedited files). Close with a report: files changed; occurrences found and deliberately left, each with its reason; and adjacent inconsistencies noticed along the way that the change's scope did not cover.

## Consequences the command accepts

An in-place revision changes the active head's text underneath any side artifacts stamped against it. The stamps still name the right file, so nothing becomes detectably `stale` — the freshness predicate compares filenames, not content (see the Artifact-state section of `agents/orchestrator.md`). This is accepted by design: a revision never touches freshness or review state. "Review state" here means the artifact-level review gate — `agents/orchestrator.md`'s Artifact-state `Reviewed-draft:` pending-vs-decided status — which this command still never touches; it is a different thing from the per-entry `unreviewed`/`confirmed` confirmation marker that Apply (step 6) flips (an unfortunate naming collision, since `continuity/`'s and `knowledge/`'s marker field is itself named `- **review:**`), which is exactly the write this command performs by design, on both the confirm-only and correct-and-confirm paths. When it matters, the human reruns the relevant report step; the closing report names any stamped side artifacts produced against the pre-revision text so the human can decide.

## Failure modes

Stop and ask the human, in plain text, when any of these hold. Describe the problem; do not guess, and do not touch any state file.

- The change description is ambiguous and the ambiguity affects what gets edited.
- The change collides with locked structure — an immutable marker, a reveal-timing constraint — in a way the request does not already resolve.
- New-draft mode was requested but no draft exists in `<latest-attempt>`: there is nothing to revise; the drafting step has not run.
- The attempt manifest is malformed, or missing when new-draft mode must append to it. (In-place mode tolerates a missing manifest: `<latest-draft>` falls back per `agents/project-layouts.md`.)
